# 阶段 2C-2.2 真实大模型 Bad Case 修复验收

## 1. 两个原始 Bad Case

1. 真实模型以 `final_answer=""`、`tool_arguments={}` 表达语义空值，违反严格 JSON `null` Contract。
2. 用户询问没有 Tool、Facts 或规则知识支持的退款问题时，模型曾暗示可以查询退款进度。

本次使用真实 OpenAI-compatible 中转 Provider（实际模型 `gpt-5.5`）、`RealLLMDecisionModel`、完整 Orchestrator 和已配置的 Java facts API。未使用 Fake、Mock、Stub 或预设决策，未访问或修改 Java 项目源码。

## 2. Output Normalization 规则

在 Provider JSON 与 `AgentDecision` Pydantic 校验之间新增 `normalize_agent_decision_payload`：

| 原始控制字段值 | 归一化结果 |
| --- | --- |
| `final_answer=""` 或仅空白 | `null` |
| `tool_name=""` 或仅空白 | `null` |
| `tool_arguments={}` | `null` |

归一化之后仍依次经过 Pydantic、语义、Capability、Registry、Tool 参数、Evidence、去重与终止校验。它不改变 action 或执行路径。

## 3. 明确不会 Normalize 的错误

- 非空 `final_answer` 不会被删除。
- 未知/未授权 Tool 不会改写为合法 Tool。
- `userId` 等敏感或额外 Tool 参数不会删除，仍由严格参数 Schema 拒绝。
- 非法 evidence path、错误 action、错误 Tool 名称、未知参数和 `missing_information=null` 均不会自动修复。

因此该层只处理明确的 null 表达差异，不降低 Harness 安全标准。

## 4. Capability Prompt 调整

Prompt 以最小改动明确：`available_tools` 是 Agent 当前完整的可执行能力集合，不是示例；模型不得假定未列出的 Tool、业务查询、实时状态来源或规则知识。若平台事实/规则既不在当前 Facts 中，也不能由已列 Tool 取得，必须 `HANDOFF` 并说明缺失信息。Prompt 同时要求 nullable 控制字段输出 JSON `null`，不用空字符串或空对象。

没有加入退款关键词分支、固定问题分类、订单诊断 `if/else` 或新业务 Tool。

## 5. 单元测试结果

新增独立归一化测试覆盖：CALL_TOOL 空 `final_answer`、ANSWER/HANDOFF 空 Tool 参数、空白字符串、非空答案保留、`userId` 保留后被参数校验拒绝、`refund_order` 不改写。环境加载与既有回归保持通过。

```powershell
conda run -n group-buy-agent python -m pytest -q
```

结果：`55 passed in 0.32s`。

## 6. 场景 A 真实结果

输入：`你能帮我做什么？`

| 项目 | 实际结果 |
| --- | --- |
| 最终状态 | `FINISHED` |
| action | `ANSWER` |
| Tool 调用数 | 0 |
| 模型调用 / 重试 | 1 / 0 |
| Normalization | 未发生（Provider 直接输出正确 `null`） |
| used_evidence | `[]` |

最终回答为通用能力说明，没有声称额外 Tool 或未提供的业务查询能力。

## 7. 场景 B 第一次 Model Decision

输入：订单未成团问题（运行时可信身份注入，未写入报告）。

第一次真实决策：

```text
action = CALL_TOOL
tool_name = get_order_facts
tool_arguments = {"outTradeNo": "644398015396"}
final_answer = null
missing_information = []
```

没有 `userId`、可信身份、Header、SQL、`base_url`、`teamId` 或 `activityId`；Normalization 未发生，因为 Provider 已输出正确的 `null`。决策通过 Harness 并执行 Tool。

## 8. Tool 调用与 Java/MySQL 真实 Facts

场景 B 的 `get_order_facts` 实际执行一次：`ToolResult.success=true`、`source=java_market`，Trace 中 Tool 调用耗时为 19 ms。返回的本次规范化 Facts 写入 `ContextState.order_facts`、evidence 与 ToolResult：

```text
order.status = CLOSE
team.status = PROGRESS
team.target_count = 3
team.lock_count = 0
team.complete_count = 0
team.valid_end_time = 2026-07-30T03:45:37+08:00
activity.status = EFFECTIVE
references.team_id = 18781389
references.activity_id = 100123
```

evidence 包含 `order.status`、`team.status`、`team.targetCount`、`team.completeCount`、`activity.status`，均来自 `java_market`。这证明 Agent → Tool → Java HTTP facts 路径真实运行；本项目不直接访问 MySQL，MySQL 由 Java 服务边界负责。

## 9. 第二次 Model Decision、最终 ANSWER 与 used_evidence

Tool observation 后，真实模型被再次调用，说明 Facts 已进入第二轮模型 Context。两次真实 `ANSWER` 都基于返回的订单/拼团/活动状态说明未达到 3 人成团条件并提及订单关闭。

但两次都有以下未修复 Contract 问题：

```text
missing_information = null     # Contract 要求 string[]
used_evidence = facts.order.status, facts.team.status, ...
                              # 实际可用 path 为 order.status、team.status、...
```

`missing_information=null` 不属于本阶段允许的 nullable 控制字段，故未被 Normalize；Pydantic 先拒绝为 `MODEL_CONTRACT_MISMATCH`。即使该字段正确，`facts.` 前缀也会被 Evidence Validation 拒绝。两次有限模型尝试后状态为 `HANDOFF`，没有通过 Harness 的最终 ANSWER 或 `used_evidence`。

## 10. 场景 C 结果

输入：`我的退款什么时候到账？`

模型选择 `HANDOFF`，但两次均以非空 `final_answer` 声称“提供订单号后可以查询退款状态/到账时间”。这既违反 HANDOFF 的 `final_answer=null` Contract，也错误暗示当前不存在的退款查询能力。Harness 两次 `MODEL_CONTRACT_MISMATCH` 后安全转人工，没有 Tool 调用、退款事实或规则被编造为系统结果。

- B：`ROUTED → MODEL_DECISION(CALL_TOOL) → TOOL_CALL(get_order_facts) → TOOL_RESULT(success) → MODEL_VALIDATION_ERROR × 2 → HANDOFF`

## 13. 新增或仍存在的 Bad Case

1. 原始 `""` / `{}` 空值问题：本次真实输出未再出现；归一化由单元测试验证，live 未触发。
2. 第二轮 ANSWER 的 `missing_information=null`：不在本阶段窄归一化范围，仍被严格拒绝。
3. 第二轮 `used_evidence` 错误使用 `facts.` 前缀：不会自动修复，仍会被 Evidence Validation 拒绝。
4. 退款问题仍错误宣称可查询退款信息：能力边界 Prompt 未完全消除该 Provider 行为，安全 Harness 已阻止其成为最终对用户的错误答案。
