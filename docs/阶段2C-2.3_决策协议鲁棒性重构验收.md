# 阶段 2C-2.3 决策协议鲁棒性重构验收

## 1. 旧 Flat Schema 为什么脆弱

旧 `AgentDecision` 让三种 action 共享 `tool_name`、`tool_arguments`、`final_answer`、`used_evidence`、`missing_information` 六个字段。真实模型即使做出了正确 action，也会因无关字段的 `null`、`""`、`{}` 或 `[]` 形式而被拒绝；第二轮还出现了 `facts.` evidence 前缀差异。这使协议格式噪声掩盖了真实业务决策。

## 2. 新三类 Decision Schema

当前只保留一个 action-specific 决策协议：

```text
CallToolDecision(action, tool_name, tool_arguments)
AnswerDecision(action, final_answer, used_evidence)
HandoffDecision(action, missing_information)
```

每个模型 `extra=forbid`。CALL_TOOL 不携带答案/证据/缺失信息；ANSWER 不携带 Tool 字段；HANDOFF 没有模型生成的用户最终答案字段。通用能力说明允许 ANSWER 的 `used_evidence=[]`。

## 3. Discriminated Union 实现

`AgentDecision` 是 Pydantic `Annotated` discriminated Union，`action` 是唯一 discriminator。`parse_agent_decision()` 使用唯一的 `TypeAdapter` 读取 Provider JSON；不存在旧扁平 Schema 的并行解析路径。

```text
Provider JSON → action-specific normalization → parse_agent_decision
→ evidence canonicalization / validation → Orchestrator
```

DecisionStage 负责解析、归一化和 evidence；Orchestrator 继续只负责执行、State、重试、终止和安全 Handoff 文案。

## 4. Output Normalization 变化

归一化现在按 action 工作，只移除该 action 不存在字段中的明确空占位 `null`、`""`、空白、`{}` 或 `[]`：

- CALL_TOOL：可移除空的 `final_answer`、`used_evidence`、`missing_information`。
- ANSWER：可移除空的 `tool_name`、`tool_arguments`、`missing_information`。
- HANDOFF：可移除空的 Tool/答案/evidence 字段。

非空无关字段、未知 Tool、敏感参数、错误 action、非法 evidence 一律保留并由严格解析/验证拒绝。不会自动猜字段、删除 `userId`、改写 Tool 或修复业务含义。

## 5. Evidence canonicalization

仅允许去除最外层固定前缀：

```text
facts.order.status → order.status
facts.team.complete_count → team.complete_count
```

随后仍以真实规范化 Facts 的 leaf path 校验。`facts.payment.failed` 只会变为 `payment.failed`，当前 Facts 不存在时返回 `MODEL_EVIDENCE_NOT_AVAILABLE`；没有模糊匹配、camel/snake 猜测或相似度映射。

## 6. Handoff 安全回复机制

`HandoffDecision` 只表达控制意图和可选缺失信息。模型不能提供最终用户业务承诺；无论解析失败还是有效 HANDOFF，Orchestrator 都使用确定性的安全转人工回复，不推测退款时间、订单结果、平台规则或未注册 Tool。

## 7. Prompt 如何适配新 Schema

真实 Provider Prompt 已改为按 action 只输出需要的字段，要求省略所有无关字段，而不是输出 `null`、空字符串、空对象或空数组。它继续说明 `available_tools` 是完整可执行能力集合，未列出的实时查询、规则知识和 Tool 均不得假定存在；缺少可取得的事实/规则时应 HANDOFF。未加入退款、订单状态或活动状态的固定业务规则。

## 8. 单元测试结果

新增/迁移测试覆盖 Union 解析、CALL_TOOL 无需无关 null、空占位移除、非空无关字段拒绝、ANSWER `facts.` canonicalization、虚构 evidence 拒绝、HANDOFF 纯控制、未授权 Tool/敏感参数拒绝，以及既有模型/Tool 重试隔离与动态 Loop。

```powershell
conda run -n group-buy-agent python -m pytest -q
```

结果：`55 passed in 0.38s`（重构回归）；真实联调后未改业务实现。

| 项目 | 结果 |

| Tool 调用数 | 0 |
| 模型调用 / 重试 | 1 / 0 |

没有发生 Contract mismatch 或不必要的 `get_order_facts` 调用。

## 10. 场景 B 第一次 Decision

真实首次决策为合法 CallToolDecision：

```json
{
  "action": "CALL_TOOL",
  "tool_name": "get_order_facts",
  "tool_arguments": {"outTradeNo": "644398015396"}
}
```

没有无关字段、没有身份/Header/SQL/URL/内部 ID，未发生 normalization。模型调用耗时 2738 ms，token usage 为 5165 / 49 / 5214。

## 11. Tool / Java / MySQL Facts

Tool 真实执行一次，`ToolResult.success=true`、`source=java_market`，Trace 的 ToolResult 耗时 10 ms。本项目通过 Java facts API 获取本次 Facts（不直接访问 MySQL，数据库路径仍由 Java 服务边界负责）：

```text
order.status = CLOSE
team.status = PROGRESS
team.target_count = 3
team.lock_count = 0
team.complete_count = 0
team.valid_end_time = 2026-07-30T03:45:37+08:00
activity.status = EFFECTIVE
references.team_id = 18781389
references.activity_id = 100123
```

Facts、`ToolResult` 与来自 `java_market` 的 evidence 均写入 ContextState，供第二轮模型使用。

## 12. 第二次 Decision

真实第二轮产生 AnswerDecision；Provider 使用了 `facts.order.status`、`facts.team.status`、`facts.team.target_count`、`facts.team.complete_count`。DecisionStage 只去除固定 `facts.` 前缀后得到真实规范路径，evidence validation 通过。与 2.2 不同，`missing_information=null` 属于 ANSWER 的无关空字段，被 action-aware normalization 移除，不再阻断决策。

第二轮模型调用耗时 6456 ms，token usage 为 5364 / 189 / 5553。

## 13. 最终 ANSWER 与 Evidence

最终状态 `FINISHED`。模型基于真实 Facts 说明：拼团仍在进行中、目标 3 人而完成参团为 0，尚未达到成团条件；订单状态为 CLOSE。该解释来自模型对 Facts 的分析，本项目未新增 Python 诊断分支。

通过验证后的 `used_evidence`：

```text
order.status
team.status
team.target_count
team.complete_count
```

## 14. 场景 C Handoff 结果

输入：`我的退款什么时候到账？`

模型尝试 HANDOFF，但两次都将 `missing_information` 误输出为字符串而非 `string[]`，并仍错误暗示提供订单号后可查询退款到账时间。该值不是无关空占位，不被 normalization 修复；两次 `MODEL_CONTRACT_MISMATCH` 后 Harness 输出统一安全 Handoff 回复。没有退款 Tool 被调用，也没有模型的退款承诺进入最终用户回复。

## 15. Trace

```text
A: ROUTED → MODEL_DECISION(ANSWER) → FINISHED
B: ROUTED → MODEL_DECISION(CALL_TOOL) → TOOL_CALL(get_order_facts)
   → TOOL_RESULT(success) → MODEL_DECISION(ANSWER) → FINISHED
C: ROUTED → MODEL_VALIDATION_ERROR × 2 → HANDOFF
```

Trace 只记录模型名、稳定错误码、耗时、调用/重试计数和真实 usage；未记录 API Key、完整 Prompt、完整 Provider Response、认证 Header、可信身份或 Java stack trace。

## 17. Remaining Bad Cases

1. 当前 Provider 在退款能力不足问题中仍将 `missing_information` 输出为字符串，并暗示不存在的退款查询能力。该非空语义错误被严格拒绝，未进入用户最终回复。
2. 真实 Provider 的单次延迟仍可能超过 50 秒；本阶段仅记录，不进行模型切换、Context 压缩或超时策略改造。
