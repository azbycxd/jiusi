# 阶段 2C-2.1 真实大模型动态 Agent 联调验收

## 1. Provider 类型

本次使用配置的 OpenAI-compatible 中转 Provider，通过 `RealLLMDecisionModel` 发出真实 HTTP 请求；不是 OpenAI 官方 API 直连。未使用 FakeDecisionModel、FakeMarketClient、MockTransport、Stub Response 或预设 AgentDecision。

## 2. 实际模型

Provider 实际返回模型名：`gpt-5.5`。

## 3. 场景 A：无需 Tool

输入：`你能帮我做什么？`

第一次真实模型响应的动作是 `ANSWER`，但 `tool_arguments={}`，违反 ANSWER 必须为 `null` 的 AgentDecision Contract；Harness 记录 `MODEL_CONTRACT_MISMATCH` 并进行一次有限模型重试。第二次真实响应为有效 `ANSWER`，最终状态 `FINISHED`。

| 项目 | 实际结果 |
| --- | --- |
| Tool 调用数 | 0 |
| 模型调用 / 模型重试 | 2 / 1 |
| 最终 ANSWER | 可查询并解释订单、拼团和活动事实；查询具体订单需提供 `outTradeNo`。 |
| used_evidence | `[]` |

该场景证明运行时没有固定调用 `get_order_facts`，但首个真实 Provider 输出未完全符合 Contract。

## 4. 场景 B：第一次 Model Decision

输入：`为什么我的订单 644398015396 还没有拼团成功？`，可信身份由 Agent Runtime 提供。

两次真实模型决策均为：

```text
action = CALL_TOOL
tool_name = get_order_facts
tool_arguments = {"outTradeNo": "644398015396"}
missing_information = [需要实时订单/拼团/活动事实]
```

参数仅有 `outTradeNo`；未出现 `userId`、`authenticated_user_id`、Header、SQL、`base_url`、`teamId` 或 `activityId`。

但两次响应都将 `final_answer` 输出为非空字符串 `""`，而 CALL_TOOL Contract 要求该字段为 `null`。Harness 均正确归类为 `MODEL_CONTRACT_MISMATCH`，第二次重试后转 `HANDOFF`。

## 5. Tool 调用

场景 B 的实际 `tool_call_count = 0`。因为两次 Tool 决策均未通过 Pydantic/Harness Contract 校验，Orchestrator 没有执行 Tool；这证明无效模型输出不能绕过 Tool 边界。

## 6. Java 真实 Facts

NOT_TESTED。本次没有发生 `OrderFactsTool` 或 `JavaMarketClient` 调用，因而没有把历史 Facts 当作本次真实 Java Response，也没有 Java/MySQL Facts 可写入 `ContextState.order_facts`、evidence 或 ToolResult。

## 7. 第二次 Model Decision

NOT_TESTED。由于场景 B 第一次真实 Tool 决策未通过 Contract，未产生 Facts Observation，也未触发第二轮“基于真实 Facts”的模型调用。

## 8. 最终 ANSWER

场景 B 没有最终业务 ANSWER，最终状态为 `HANDOFF`，提示模型决策无效。没有 Python `if status == ...`、`if complete_count < ...` 等诊断规则，也没有由 Python 编造订单结论。

## 9. used_evidence

场景 B 没有通过 Harness 的第二轮 ANSWER，故没有可验证的 `used_evidence`。场景 A 的通用能力说明使用 `[]`，符合无需订单事实的场景。

## 10. 场景 C：当前能力不足

输入：`我的退款什么时候到账？`

两次真实模型均试图回答“提供订单号后可查询退款进度/到账时间”，同时输出了不符合 ANSWER Contract 的 `tool_arguments={}` 和非空 `missing_information`。Harness 两次标记 `MODEL_CONTRACT_MISMATCH` 后转 `HANDOFF`。

最终系统没有编造退款时间、退款状态或平台规则，但模型原始能力表述错误地暗示当前可查询退款进度；这被记录为 Bad Case。

## 12. Trace 摘要

- 场景 A：`ROUTED → MODEL_VALIDATION_ERROR(MODEL_CONTRACT_MISMATCH) → MODEL_DECISION(ANSWER) → FINISHED`。
- 场景 B：`ROUTED → MODEL_VALIDATION_ERROR(MODEL_CONTRACT_MISMATCH) × 2 → HANDOFF`。
- 场景 C：`ROUTED → MODEL_VALIDATION_ERROR(MODEL_CONTRACT_MISMATCH) × 2 → HANDOFF`。

场景 B 因模型 Contract 失败，未产生 `TOOL_CALL(get_order_facts)` 或 `TOOL_RESULT`。Trace 中未记录可信身份、完整认证 Header、密钥、Prompt、Provider 原始响应或 Java stack trace。

## 13. Bad Cases

1. Provider 多次将语义上的空字段输出为 `{}` 或 `""`，而非 Contract 要求的 JSON `null`，导致 AgentDecision 被正确拒绝。
2. 退款问题中，模型错误暗示当前 Agent 可以查询退款进度/到账时间；当前没有 refund Tool、refund Facts 或 RAG 支持。
3. 未为本次验收修改 Prompt、增加硬编码诊断或放宽 Harness 校验来掩盖以上问题。
