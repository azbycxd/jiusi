# 阶段 2C-2.4 Handoff 决策协议收尾验收

## 1. 原始 Bad Case

阶段 2C-2.3 中，真实模型在退款能力不足场景已选择 `HANDOFF`，但把 `missing_information` 输出为单个字符串。正式 `HandoffDecision` 要求 `list[str]`，导致两次 `MODEL_CONTRACT_MISMATCH` 与无意义模型重试。

## 2. missing_information string → list 规则

仅在 `action == HANDOFF` 且 `missing_information` 为非空字符串时，Normalization 将其原样包装：

```text
"缺少退款状态事实" → ["缺少退款状态事实"]
```

只改变容器，不修改字符串内容、不总结、不补充，也不依据退款等业务词汇决定是否转换。`HandoffDecision` 正式 Schema 仍严格是 `missing_information: list[str]`。

## 3. 明确不会 Normalize 的情况

- `missing_information=123`、`{}`、`[123]`、`["合法", 123]` 仍被 Pydantic 拒绝。
- ANSWER 或 CALL_TOOL 的 `missing_information="xxx"` 不会 string→list。
- 未知 Tool、`userId` 等额外参数、非空无关字段、错误 action 和非法 evidence 仍不改写。
- 空字符串按既有空占位策略移除；Schema 默认的空缺失信息不会被凭空补充。

## 4. 是否修改 Prompt

否。本阶段未修改 `decision/real_llm.py` 中的 Prompt，也没有退款示例、退款关键词规则或 Prompt Engineering。

## 5. 单元测试结果

新增 Handoff string/list、空占位、非法类型、非 HANDOFF action 不归一化和安全最终文案测试；既有 Decision Union、evidence、Tool、模型/Tool retry 与动态 Loop 测试继续通过。

```powershell
conda run -n group-buy-agent python -m pytest -q
```

结果：`58 passed in 0.40s`。

## 6. 场景 A

输入：`你能帮我做什么？`

真实 `gpt-5.5` 一次有效 AnswerDecision，最终 `FINISHED`，`tool_call_count=0`、`model_call_count=1`、`model_retry_count=0`。模型耗时 9182 ms，token usage 为 5157 / 290 / 5447。没有 Contract mismatch。

## 7. 场景 B 完整主链路回归

输入：订单未成团问题（可信身份仅在运行时注入，未记录在报告）。

真实链路保持通过：

```text
LLM CallToolDecision
→ get_order_facts
→ Java facts API / Java 数据边界
→ ToolResult / ContextState Facts / evidence
→ LLM AnswerDecision
→ evidence canonicalization / validation
→ FINISHED
```

首次模型调用 2331 ms，`tool_call_count=1`；ToolResult 成功，Trace ToolResult 耗时 13 ms。第二轮模型调用 31838 ms，最终 `FINISHED`，没有模型重试。

本次真实 Facts：订单 `CLOSE`；拼团 `PROGRESS`、目标 3 人、完成 0 人；活动 `EFFECTIVE`。Python 不直接访问 MySQL，数据库路径仍由 Java 服务负责。

## 8. 场景 C 原始模型 Decision

输入：`我的退款什么时候到账？`

真实模型一次输出：

```json
{
  "action": "HANDOFF",
  "missing_information": "需要外部订单号 `outTradeNo` 才能查询退款到账时间。"
}
```

没有 Tool 调用。字符串中的能力暗示仅作为模型内部 metadata；不会被当成用户答复或执行退款查询。

## 9. Normalization 前后值

```text
before: "需要外部订单号 `outTradeNo` 才能查询退款到账时间。"
after:  ["需要外部订单号 `outTradeNo` 才能查询退款到账时间。"]
```

`normalization_applied=true`；字符串内容逐字保留。

## 10. HandoffDecision

归一化后，数据通过严格 `HandoffDecision(action=HANDOFF, missing_information=list[str])` 解析。没有 `MODEL_CONTRACT_MISMATCH`，无需第二次模型调用。

## 11. 最终安全回复

最终状态为 `HANDOFF`。用户可见文案由 Orchestrator 的统一安全回复生成：`模型建议转人工客服处理。` 它不包含模型 metadata 中“提供订单号后可查询退款”的错误承诺，也不推测退款时间、状态、平台规则或未注册 Tool。

## 15. Remaining Bad Cases

Provider 的 Handoff metadata 仍可能表达超出当前能力的退款查询假设，但它只能停留在内部 `missing_information`，不触发 Tool，也不进入最终用户回复。该阶段不通过 Prompt 或退款专用规则继续处理。
