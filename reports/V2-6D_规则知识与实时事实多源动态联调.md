## 2. Python baseline

开始前执行完整测试：`128 passed in 1.29s`。

## 3. 三 Tool 状态

真实运行时 `available_tools` 只包含：

```text
get_order_facts
get_joinable_team_facts
search_group_buy_rules
```

三者分别用于当前订单/团队事实、当前可加入候选团队事实、稳定规则知识；没有固定预选工具。

## 4. 场景 A：纯成团规则

问题“拼团一般达到什么条件才算成团？”实际路径：

```text
search_group_buy_rules -> ANSWER -> FINISHED
```

仅调用规则 Tool（`tool_call_count=1`），最终引用 `search_group_buy_rules.results.0.content`，回答说明完成支付人数达到目标人数才完成。未调用任何实时 Facts Tool。一次最终模型 timeout 由现有有限重试恢复。

## 5. 场景 B：人数指标解释

首次请求经历两次 `MODEL_TIMEOUT`，未得到模型决策，归类为 `PROVIDER_RELIABILITY`。未改变参数后，以新的独立 session 重试：

```text
search_group_buy_rules -> ANSWER -> FINISHED
```

仅使用规则 Evidence，正确解释 `targetCount`、`lockCount`、`completeCount`，并声明具体数值需要实时查询。

## 6. 场景 C：纯订单事实

问题“订单 644398015396 当前是什么状态？”实际路径：

```text
get_order_facts -> ANSWER -> FINISHED
```

仅调用订单 Facts Tool（`tool_call_count=1`），没有调用 RAG。真实结果中订单为 `CLOSE`、团队为 `PROGRESS`、活动为 `EFFECTIVE`；最终 Evidence 仅来自 `get_order_facts`。

## 7. 核心场景 D Run #1

```text
get_order_facts -> search_group_buy_rules -> ANSWER -> FINISHED
```

`model_call_count=3`、`tool_call_count=2`、`retry_count=0`。最终同时引用订单/团队实时 Evidence 与规则内容，区分了“当前 0/3、PROGRESS”的事实和“一般完成支付人数达到目标人数”的规则。

## 8. 核心场景 D Run #2

同一用户问题使用新 session，实际路径仍为：

```text
get_order_facts -> search_group_buy_rules -> ANSWER -> FINISHED
```

`model_call_count=3`、`tool_call_count=2`、`retry_count=0`。最终 Evidence 同时覆盖 `get_order_facts.team.status`、`target_count`、`complete_count` 和 `search_group_buy_rules.results.0.content`。

## 9. 核心场景 D Run #3

新 session 下仍完成相同的两源选择与有效 ANSWER：

```text
get_order_facts -> search_group_buy_rules -> ANSWER -> FINISHED
```

`model_call_count=4`、`model_retry_count=1`、`tool_call_count=2`、`retry_count=0`。一次最终模型 timeout 由既有重试恢复；没有 Tool 重试、重复调用阻断或终止异常。

## 10. Multi-Source Evidence

三个 D Run 的最终 `used_evidence` 均同时包含可验证路径：

```text
get_order_facts.team.status
get_order_facts.team.target_count
get_order_facts.team.complete_count
search_group_buy_rules.results.0.content
```

同时出现的订单状态、活动状态等路径均来自对应 Facts Observation。所有路径通过现有 Hard Evidence Guard；没有把规则当作当前人数事实，也没有把实时事实当作通用规则。

## 11. 场景 E：订单 + CLOSE

问题包含具体订单和 CLOSE 退款语义。真实动态顺序为：

```text
search_group_buy_rules -> get_order_facts -> ANSWER -> FINISHED
```

这与 D 的 Facts→RAG 顺序不同，证明没有固定 Multi-Source Workflow。最终同时引用 `get_order_facts.order.status` 和规则 content，并明确：CLOSE 只表示本地退单关闭状态，不能证明支付渠道退款完成、退款金额或到账时间。`model_retry_count=1` 的 Provider timeout 成功恢复。

## 12. 场景 F：纯 CLOSE 语义

无具体订单时路径为：

```text
search_group_buy_rules -> ANSWER -> FINISHED
```

仅使用 CLOSE 规则内容，明确拒绝由 CLOSE 推断资金到账；没有调用订单 Facts Tool。

## 13. 场景 G：实时资格边界

“我现在还能参加这个活动吗？”在没有完整资格 Facts Tool 的情况下直接：

```text
HANDOFF
```

`tool_call_count=0`。模型没有用规则知识替代 Java 的实时资格判定，也没有编造可参加/不可参加结论。

## 14. 场景 H：实时可加入团队

路径为：

```text
get_joinable_team_facts -> ANSWER -> FINISHED
```

仅调用实时团队 Facts Tool。真实 `candidate_teams=[]`，且统计为总团队 1、已成团 1、参与人数 3；最终 Evidence 都来自该 Tool，没有调用 RAG。回答语义为当前可加入候选团队为空，不将其解释为活动不存在其他团队。

## 15. 场景 I：实时团队 + 筛选规则

实际路径为：

```text
get_joinable_team_facts -> search_group_buy_rules -> ANSWER -> FINISHED
```

最终同时引用 `get_joinable_team_facts.candidate_teams`、统计事实与规则内容。回答把当前候选列表为空与一般筛选因素（可继续拼单状态、容量、有效期、用户关系等）分开表述，未以规则替代当前候选 Facts。

## 16. 场景 J：无关问题

“今天天气怎么样？”直接 `HANDOFF`，`tool_call_count=0`。没有强行检索规则或调用任何业务 Facts Tool。
