# V2-6C：拼团规则检索工具接入

## 1. 执行对象与项目边界

本阶段只修改 `group-buy-agent` Python 项目。仅消费用户提供并审核通过的 `group_buy_rules_v1.json` 知识产物；没有读取 Java 源码、没有修改 Java 项目、数据库或服务，也没有新增任何规则正文。

## 2. Catalog 导入位置与版本

Catalog 导入至 `knowledge/catalogs/group_buy_rules_v1.json`。解析后的 JSON 内容与用户提供的产物一致，Catalog 为 `group_buy_rules`、版本 `v1`、`entry_count=15`。

## 3. Knowledge Contract

新增严格 Pydantic Contract：

- `KnowledgeCatalog`：`catalog`、`version`、`generated_from`、`review_date`、`entry_count`、`entries`；禁止额外字段。
- `KnowledgeEntry`：覆盖所需治理及规则字段；`source_level` 仅允许 `LEVEL_1`、`LEVEL_2`、`LEVEL_3`。
- Loader 校验 `entry_count == len(entries)`、`knowledge_id` 唯一、必要文本非空，且治理字段/tags 列表不为空且不含空值。

无效数量、重复 ID、非法来源等级均在加载边界被拒绝。

## 4. 治理字段与模型可见字段分离

Catalog 内的 `source_files`、`source_symbols` 与 `generated_from` 仅在本地治理 Contract 中保留。模型可见 Tool data 只投影：

```text
knowledge_id, title, category, content, source_level, requires_realtime_facts
```

测试确认 ToolResult、Observation 与后续 DecisionContext 中不含治理字段、内部源码目录、类名、包名或符号名。

## 5. Retriever 抽象

新增窄接口 `RuleRetriever.search(query) -> RuleSearchResult`。`SearchGroupBuyRulesTool` 仅依赖该接口；后续可替换为 Embedding Retriever，而无需改 Tool、Registry、Observation 或 DecisionContext。

## 6. 第一版检索算法

`LexicalRuleRetriever` 是确定性、无外部依赖的 baseline：

- query 规范化；
- 中文 bi-gram overlap；
- 完整 ASCII token overlap；
- title、category、tags、content 的加权匹配；
- 精确/包含匹配 boost；
- 固定 `top_k=3`，按 `score DESC`、`knowledge_id ASC` 稳定排序。

单字符特征未参与匹配，避免普通中文字符或英文子串导致无关命中。

## 7. Tool Contract

新增只读 Tool `search_group_buy_rules`：

- arguments 仅为严格的 `query`；去空白后不能为空，最大 500 字符，`extra=forbid`。
- 不接受 `topK`、`limit`、文件路径、SQL、用户身份、Token、Header 或 embedding 参数。
- 描述明确它查询稳定的拼团规则、状态含义与退单语义，不是实时订单/团队/活动事实查询。
- 成功 source 为 `knowledge_catalog`，不伪装为实时市场事实来源。

## 8. Registry / Capability

默认 Registry 与 Capability allowlist 现在恰好允许三个 Tool：

```text
get_order_facts
get_joinable_team_facts
search_group_buy_rules
```

Registry 保持 generic，没有针对新 Tool 的名称分支。

## 9. RepeatPolicy

规则 Catalog 为进程内稳定只读数据。新 Tool 使用 `repeatable=False`、`max_same_call=1`：同一 canonical query 的第二次调用被 Loop Guard 阻止；不同 query 仍可连续检索。

## 10. Observation / Evidence

成功检索产生标准 Observation。非空结果 Evidence 包括 catalog 版本及每条结果的 `knowledge_id`、`title`、`content`、`requires_realtime_facts`，路径如：

```text
search_group_buy_rules.results.0.content
```

真实 Evidence 可通过现有 ANSWER Validation；虚构的 `source_files` Evidence 仍被 Hard Evidence Guard 拒绝。

## 11. 空结果语义

低匹配或无关 query 返回 `results=[]`，仍为 `ToolResult.success=True`。Tool 显式产生 `results=[]` Evidence，复用既有空 list terminal Evidence Contract，不把“没有规则命中”错误地转为 HANDOFF 或 Tool failure。

## 12. requires_realtime_facts 语义

该字段随检索结果进入模型可见数据，表示规则只能说明一般语义，不能单独证明某个用户、订单、团队或活动的当前状态。Tool 不自动调用 Java，也不生成最终业务判断；下一轮是否调用实时 Facts Tool 仍由受控 DecisionStage 决定。

## 13. Retrieval Eval Set

评测集包含 20 条自然语言中文 query，覆盖流程、开团/参团、成团条件、人数语义、团队/订单状态、活动有效期、参与次数、标签、优惠、候选团队、超时未支付、未成团退单、已成团退单和 CLOSE 退款边界。另含 5 条明显无关 query：天气、Python 排序、股票、餐饮、降雨。

## 14. Top-1 Hit Rate

`0.70`（14 / 20）。这是记录指标，不作为本阶段硬门槛。

## 15. Top-3 Hit Rate

`1.00`（20 / 20），高于 baseline 验收线 `0.90`。

## 16. 无关 Query 结果

五条无关 query 均返回 `results=[]`，没有被强行匹配为拼团规则。

## 17. 隐私/内部源码隔离

治理追踪字段保留在本地 Catalog Loader 边界；ToolResult、Observation、DecisionContext 和 Evidence 不携带内部来源。未将 Catalog 文件路径作为 Evidence。

## 19. 是否需要升级 Embedding/Vector Retrieval

当前不需要。15 条审核规则上的确定性 Lexical baseline Top-3 达到 `1.00`，且无关 query 拒绝正常。Embedding/Vector Retrieval 保留为以后真实 retrieval eval 退化时的可替换实现，不在本阶段引入。

## 20. Remaining Issues

- 尚未进行 Real LLM + 规则知识 + Java Facts 的综合动态选择验收；该项属于 V2-6D。
- 当前 Top-1 为 `0.70`，后续应在扩展 Catalog 或真实 query 集变化后持续评测，而不是预先加入重量级检索基础设施。
