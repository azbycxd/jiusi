未出现 `ROUTED(action=legacy_route)` 或 `TOOL_REPEAT_BLOCKED`。核心 Tool sequence 达到 3/3：

因此核心稳定性为 PASS；两次 Provider timeout 由既有模型重试恢复，已作为 Provider reliability telemetry 记录。

## 11. 辅助场景 A：直接 activityId

输入：`活动 100123 现在还有其它可以加入的团吗？`

真实结果：

```text
CALL_TOOL get_joinable_team_facts({activityId: 100123})
→ ANSWER
→ FINISHED
tool_call_count=1
```

没有先调用 `get_order_facts`。ANSWER 使用 `activity_id`、空候选集合和 activity-wide statistics，且没有把统计字段等同于可加入团队数量。这证明不存在固定的 Order Tool → Joinable Tool Workflow。

## 14. 辅助场景 D：能力咨询（失败）

输入：`你现在能帮我查什么？`

真实模型没有调用 Tool，并生成了内容合理的能力说明；但其 `used_evidence` 错误引用：

```text
available_tools.get_order_facts.description
available_tools.get_joinable_team_facts.description
```

这些不是 Observation Evidence path。当前 Hard Evidence Guard 正确拒绝：

```text
MODEL_EVIDENCE_NOT_AVAILABLE
→ HANDOFF
tool_call_count=0
```

因此它不满足该场景“ANSWER 且 tool_call_count=0”的最终验收目标。

## 15. Session 隔离与固定 Workflow

所有核心与辅助真实请求均使用不同的随机 session id。每个第一轮 DecisionContext 的 Observation/Evidence 均为空，前一场景的 `tool_call_history`、Observation、Evidence 与 final state 未进入后续场景。

直接 activityId 场景只调用 Joinable Tool；纯订单场景只调用 Order Tool；退款场景不调用 Tool。这些真实行为共同证明没有固定 Workflow。

## 16. Failure 分类与最小修复建议

失败分类：`EVIDENCE`（能力咨询场景）。

Root cause：真实模型把 `available_tools` metadata 当作 ANSWER 的 `used_evidence`，而当前 Evidence Contract 的可引用来源只有 Observation。硬校验拒绝该引用是正确的。

本阶段未修复。后续应显式设计“能力说明 ANSWER 是否允许空 `used_evidence`，以及 Tool metadata 是否能作为一个独立、非业务事实的可引用来源”的契约；不能简单放宽任意 Evidence path，也不能通过 Prompt 临时强迫模型忽略该问题。

## 17. Remaining Issues

- 能力咨询场景的 metadata 引用与 Observation-only Evidence Contract 尚未对齐。
- 真实 Provider 出现了两次可恢复的最后一轮超时；核心成功，但需作为稳定性/超时配置观测项继续跟踪。
- 因能力咨询未通过，V2-5D.2 最终验收失败，不得进入 V2-6。
