# V3-2：诊断控制能力综合实现

## 1. 结论

V3-2 已完成最小 `REQUEST_INPUT → WAITING_INPUT → 同 Session 恢复` 控制闭环、诊断充分性 Prompt 收束、无对象绑定的安全失败文案修正，以及本轮最小 `DiagnosisProgress`。Progress 只保存 `goal`、`required_dimensions`、`checked_dimensions` 和 `remaining_dimensions`；没有引入 Planner、hypothesis tree、长期 Memory 或完整历史。

本轮新增 Progress 后的确定性控制测试证明：它会阻断 Eligibility 后的提前 ANSWER，阻断 Activity + Eligibility 已充分后的 Joinable Team 调用，并保持控制问题的最小 Tool 使用和 `REQUEST_INPUT` 同 Session 恢复。本次最终真实验收在 Java 预检连续成功后完成：20 个独立核心会话得到 `17/20 (85%)` FULL、`0` PARTIAL、`3` 个 Provider `MODEL_TIMEOUT` 后的有限重试 HANDOFF。所有 17 个 FULL 都完成 Activity 与 Eligibility 两个维度，未发生 Evidence 校验错误或无关 Tool 执行；整体 V3-2 验收为 PASS。

## 2. 变更范围

修改的生产侧 Python 文件：

- `decision/schemas.py`：新增严格的 `REQUEST_INPUT` Decision；它必须包含 1–5 个简短、非空的 `missing_information` 字段。
- `decision/normalization.py`：为该新 Decision 提供与 HANDOFF 一致的安全格式归一化；非空的无关字段仍由严格 Schema 拒绝。
- `agent/state.py`：新增非终态 `WAITING_INPUT`，以及仅用于本次待补充会话的 `pending_user_query`。
- `agent/orchestrator.py`：模型请求输入时保存原问题和缺失字段；同身份同 Session 的下一条消息组合为“原问题 + 用户补充信息”后继续既有 Decision Loop。终态、跨身份和新 Session 继续按既有创建新 State 的规则隔离。
- `decision/real_llm.py`：增加通用诊断充分性和“事实已足够时不扩展无关 Tool”的语义；补充 runtime-control 请求的 HANDOFF 优先级。
- `agent/orchestrator.py`：将非 Order 专属 Tool failure 的最终文案改为“所需业务事实”，不暴露 Java/SQL/内部异常，也不再错误写成“订单事实”。

没有修改 Java 项目、5 个 Tool Schema、Java HTTP Contract、RAG Catalog、trusted identity、Evidence/Provenance 基本语义、Registry/Capability allowlist、Router、Planner、V2 frozen branch，且没有添加 MCP、Multi-Agent、Vector DB、长期记忆或团队/SQL/Redis/日志 Tool。

## 3. REQUEST_INPUT 合约与会话边界

`REQUEST_INPUT` 与 `HANDOFF` 的职责严格分离：

| 决策 | 状态 | 是否需要人工 | 含义 |
|---|---|---:|---|
| `REQUEST_INPUT` | `WAITING_INPUT` | 否 | 当前能力已存在，但缺少用户可以补充的 Tool 参数 |
| `HANDOFF` | `HANDOFF` | 是 | 没有可用能力，或无法可靠继续 |

在 HTTP `POST /v1/chat` 中，`WAITING_INPUT` 会通过现有 `status`、`missing_fields` 和 `needs_human=false` 返回。例如缺少活动标识时返回 `missing_fields=["activityId"]`，不需要用户重述整个问题。

真实 Provider 验证：

1. 首轮“为什么我参加不了这个活动？”返回 `WAITING_INPUT`，请求 `activityId`，没有 Tool 调用。
2. 同 Session 补充“活动是 100123”后，模型恢复原问题并完成 `get_activity_facts → get_user_eligibility_facts → ANSWER`，证明补充值和原始目标都进入了同一轮继续路径，且不需要用户重述完整问题。

确定性测试额外验证：不同认证身份复用同一个 Session ID 时，旧 WAITING_INPUT State 不会被读取；新 Session 同样没有旧问题或缺失字段。会话记忆仍深拷贝保存，避免调用方原地篡改保存状态。

## 4. DiagnosisProgress：诊断充分性与无关 Tool 控制

保留 V3-2A 的通用原则，并补充一条最小约束：如果当前 Observation 已足以解释当前诊断范围，应 ANSWER，而不是因为 Registry 中还有能力就探索无关 Tool。

Prompt 不包含具体 Tool 名、`activityId`、固定顺序或 Activity → Eligibility → RAG Workflow。下一步 Tool 仍只能由用户问题、当前 Observation、可用 Tool metadata 和已有 Evidence 决定。

恢复后的 20 次核心评测曾取得 14 个多跳样本：Activity → Eligibility 或 Eligibility → Activity。它们均在上一份 Observation 已进入下一轮模型 Context 后选择第二个、互补的 Facts Tool，并最终以两类实时 Evidence 支撑 ANSWER。另有 5 次只使用 Eligibility 后提前 ANSWER，1 次在 Activity + Eligibility 已足够后又调用 Joinable Team，达到现有 Tool 上限后 HANDOFF。这就是引入最小 Progress 的直接依据。

Progress 初始化只在通用“开放式原因 + 失败/不能”诊断目标中发生，并从当前 Registry 中已允许、声明内部诊断维度的 Tool 收集 required dimensions；它不按 activityId、场景关键词或固定顺序挑选 Tool。Activity 和 Eligibility 是当前 Registry 声明的两个互补维度；RAG、Order Facts、Joinable Team 不属于该完成条件。

成功 Tool Observation 会把对应维度从 remaining 移到 checked。remaining 非空时 Harness 拦截 ANSWER 并让模型继续决策；remaining 为空时 Harness 不执行额外 Tool，而是让模型在同一最小 Context 下给出 ANSWER。该逻辑由 `DIAGNOSIS_PROGRESS_BLOCKED` Trace 事件记录，并由单元测试实际覆盖，不是日志字段。

DecisionContext 只新增脱敏的 `diagnosis_progress`，并继续仅提供当前用户问题、相关 Observation/Evidence、available tools。它不包含认证身份、Header、计数器、完整 AgentState、ToolResult 历史或长期 Memory。

## 5. Unknown Activity 与安全失败文案

所有非成功、非重试的 Tool failure 最终统一使用：`暂时无法获取所需业务事实，请联系人工客服协助处理。`；可重试服务耗尽时使用：`所需业务事实服务暂时不可用且重试已达上限，已转人工客服处理。`

这些文案不绑定订单或活动对象，不暴露 Java Error、SQL、Mapper、Header、认证信息或异常堆栈。确定性测试覆盖 `ACTIVITY_NOT_FOUND` 类失败，确认响应中不再包含“订单事实”或内部错误文本。恢复后的真实 Unknown Activity 已返回 `ACTIVITY_NOT_FOUND`，最终仅给出对象无关的安全失败文案，未写入 Facts Observation。

## 6. 安全回归

- **userId 注入**：初次综合评测中模型错误地选了 `REQUEST_INPUT`，但没有执行 Tool 或传递 `userId`。最终本次真实评测的注入样本返回 `HANDOFF`、`tool_call_count=0`、`missing_information=[]`；没有受保护参数进入 `REQUEST_INPUT`，也没有任何越权 Tool 调用。
- **Evidence Guard**：全量测试通过；真实评测中没有 `MODEL_EVIDENCE_NOT_AVAILABLE`。
- **RepeatPolicy**：原始超时批次仅执行既有一次额外重试，之后 HANDOFF；恢复批次无模型驱动的重复 Tool 调用。
- **trusted identity**：始终从 AgentState/可信 HTTP Header 进入 Java Client，未暴露在 DecisionContext、评测结果或报告中。
