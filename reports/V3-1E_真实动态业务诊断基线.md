## 2. Capability allowlist 审计

`CapabilityState.allowed_tools` 是实际安全边界：Orchestrator 在模型 Tool action 校验时检查它，`ToolRegistry.call` 也再次检查它。它不是直接的 DecisionContext metadata 过滤器。

`ToolRegistry` 是实际注册/执行边界，并且是 `DecisionContext.available_tools` 的唯一 metadata 来源。Tool 只在 Registry 中不会自动可执行：若 Capability allowlist 缺少它，调用仍被拒绝；Tool 只在 Capability 中而未注册，也无法展示或执行。因此新增 Tool 必须同时注册到默认 Registry 和 Capability allowlist。

结论为 `BOTH`：既有 Security allowlist，也有两份显式列表造成的 metadata duplication。当前有注册表/能力顺序与 5 Tool 的测试保护，但不共享单一声明来源，故 drift risk 为 `MEDIUM`。本阶段按要求不修改。

## 3. 评测方法与 Trace 边界

新增的评测脚本只包装真实 `RealLLMDecisionModel` 和现有 `ToolRegistry`：记录已解析的 Decision、允许的 Tool arguments、实际 ToolResult success/error、Observation tool name、Evidence kinds、计数、耗时与安全 Trace 摘要。生产 Runtime、Prompt、Tool、schema、Evidence、Registry 和 RepeatPolicy 均未改动。

核心与控制问题全部使用独立 session。`used_evidence` 是最终 Answer 的真实已解析 Decision 字段；运行时 Evidence Guard 已先于 FINISHED 校验它。

## 4. 核心诊断：5 次独立运行

问题：`为什么我参加不了活动 100123？`

| Run | Trace 摘要 | 结果 | 分类 |
| --- | --- | --- | --- |
| 1 | `MODEL_INVALID_RESPONSE → HANDOFF` | 未调用 Tool | `PROVIDER_VARIANCE` |
| 2 | `CALL get_user_eligibility_facts(activityId) → success → ANSWER` | 参与次数到达上限的事实回答 | `PARTIAL_DIAGNOSIS` |
| 3 | 同 Run 2 | 同上 | `PARTIAL_DIAGNOSIS` |
| 4 | 同 Run 2 | 同上 | `PARTIAL_DIAGNOSIS` |

四个 ANSWER 都引用 Eligibility Observation 中的参与次数、上限、限制是否已触发及相应用户约束 Evidence；没有发现 Evidence Guard failure 或将稳定规则当作实时事实。它们得出的“已达参与次数限制”是有事实依据的。

但开放式“为什么不能参加”活动不能只检查一组用户约束。四次 ANSWER 都没有查询 `get_activity_facts`，因而未验证活动状态及 `within_valid_time`，不能排除并存的活动级限制；按本阶段定义归为 `PARTIAL_DIAGNOSIS`，而非 FULL。该问题是**过早结束调查/缺少 evidence completeness 目标**，不是事实链断裂。

核心 Runs 中没有 RAG、没有重复 Tool attempt、也没有实际重复 Tool 调用。没有多 Tool 后再选择下一 Tool 的核心样本，故不能把“单 Tool 成功”当作 Planning；`OBSERVATION_DRIVEN_SELECTION_COUNT=0`，`STATIC_TOOL_SWEEP_COUNT=0`。

## 6. Observation、Evidence 与错误分类

Activity 控制场景的 Answer 使用了 `get_activity_facts.activity.*` Evidence；Eligibility 与核心 Answer 使用了 `get_user_eligibility_facts.*` Evidence；规则场景只使用 `search_group_buy_rules.*` Evidence。没有看到：

- `EVIDENCE_VALIDATION_FAILURE`；
- `RULE_AS_REALTIME_FACT`；
- `UNSUPPORTED_DIAGNOSIS`；
- `MODEL_ATTEMPTED_REPEAT` 或实际 Tool repeat；

唯一 Provider 异常是核心 Run 1 的 `MODEL_INVALID_RESPONSE`，被现有边界转换为安全 HANDOFF。唯一 Java 业务错误是 Unknown Activity 的 `ACTIVITY_NOT_FOUND`，非 retryable、无事实泄露。

## 8. DiagnosisState 与 REQUEST_INPUT 判断

真实结果支持的主要缺口是：

1. `PREMATURE_ANSWER / PARTIAL_DIAGNOSIS`：模型没有表达开放式诊断完成所需的最小 Facts set；拿到一项充分的用户侧约束后即结束。
2. `PROVIDER_VARIANCE`：一次模型无效响应，现有安全 HANDOFF 正常，但缺少更丰富的评测样本前不应归因于 Runtime。
3. `MISSING_USER_INPUT`：缺 activityId 时只能 HANDOFF，尽管可在提供 activityId 后执行已有能力。
4. `OTHER`：未知活动的安全失败文案沿用通用订单措辞，属于泛化 UX 问题。

没有观察到“已验证事实被遗忘后重复调查”“同一 Tool 重复调用”或“多轮 Tool 后丢失候选原因”的证据。因此当前证据不足以证明必须新增复杂 `DiagnosisState`；它是 `UNCERTAIN`，而不是 YES。若 V3-2 继续，应先评估最小的诊断充分性/缺失 Evidence contract，而不是预设引入 Working State。

两次 Missing Entity 都安全 HANDOFF，说明当前 contract 无法做低摩擦 slot follow-up；在 Agent 已有相应 Tool 的前提下，`REQUEST_INPUT_JUSTIFIED=YES`，但 V3-1E 不实现。
