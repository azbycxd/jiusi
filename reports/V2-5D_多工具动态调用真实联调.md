## 8. 最终 Cross-Tool Evidence 失败

真实模型的第三轮 ANSWER 合理地同时引用了订单团队事实、活动事实、候选团队查询及 activity 统计。但其中包含：

```text
get_joinable_team_facts.candidate_teams
```

当前空列表 `candidate_teams=[]` 的 ToolResult 只生成 activity/statistics Evidence；`Observation` 的列表路径解析对空列表不产生 `candidate_teams` path。因此第三轮 DecisionContext 的可用 Evidence 中不存在该路径，Harness 正确拒绝该 ANSWER：

```text
MODEL_EVIDENCE_NOT_AVAILABLE
→ HANDOFF
```

这不是模型伪造业务数据，也不是 Java Tool 失败：模型确实读取到了 Observation 中的空数组，但当前 Evidence Contract 无法为“空候选列表”提供可引用的路径。

## 11. 失败分类、Root Cause 与最小修复建议

分类：`EVIDENCE`。

Root cause：`candidate_teams=[]` 是合法 Observation data，但当前 `_data_paths()` 对空 list 返回零个路径，且 `JoinableTeamFactsTool` 未给空候选集合生成可验证的集合级 Evidence。模型无法在不引用该路径的情况下对“当前查询没有候选团队”做 cross-tool 解释；引用该真实 Observation path 后又被 Evidence validation 拒绝。

最小修复建议（本阶段未实施）：为候选集合设计一个与空数组数据完全匹配、可由 Observation validator 验证的集合级 Evidence path，例如支持 `candidate_teams` 作为空列表的可验证数据路径，并在空结果时由 Tool 生成对应 Evidence。修复后应增加：

- 空候选 ToolResult → Observation → `candidate_teams` Evidence 验证测试；
- 真实/模拟第三轮 ANSWER 使用空候选集合证据的测试；
- 完成三次核心真实联调与三个辅助场景后再评估稳定性。

不得用 Prompt 忽略 Evidence、硬编码 Tool 链、伪造候选数据或放宽 `MODEL_EVIDENCE_NOT_AVAILABLE` 来规避。
