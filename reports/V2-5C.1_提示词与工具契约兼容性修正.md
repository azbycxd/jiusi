# V2-5C.1：提示词与工具契约兼容性修正

## 1. 原 Prompt 冲突点

审计 `decision/real_llm.py` 后确认，原 SYSTEM_PROMPT 同时存在两条互相冲突的要求：

- 要求模型只使用 `available_tools` 的已发布 arguments；
- 又以 V1 单 Tool 时期的规则全局禁止 `activityId`，并把实时订单事实查询特指为 `get_order_facts`。

在 V1 仅有 `get_order_facts(outTradeNo)` 时，这种专属约束能够降低模型越权参数的概率。V2-5C 已增加合法的 `get_joinable_team_facts(activityId)` 后，它与当前 Tool Contract 冲突，并会错误地阻碍后续模型调用第二 Tool。

## 2. 修改后的通用 Tool 参数规则

SYSTEM_PROMPT 已最小化替换为以下通用规则：

- 只能请求 `available_tools` 中存在的 Tool；
- arguments 必须精确符合该 Tool 已发布的 `parameters_schema`；
- 参数值只能来自用户明确输入，或已验证的 Observation/Evidence，并且必须匹配被选 Tool 的 schema；
- 不得猜测或伪造缺失参数；
- 无法满足参数时按现有能力继续获取事实或 HANDOFF。

Prompt 不再出现 `activityId` 或 `outTradeNo` 的全局禁止/唯一合法参数表述，也没有加入任何 `get_order_facts → get_joinable_team_facts` 的固定顺序。

## 3. activityId 的合法来源

`activityId` 不是认证身份。它可以作为 `get_joinable_team_facts` 的合法参数，前提是它：

- 由用户明确提供；或
- 来自已验证 Observation/Evidence，例如 `get_order_facts.references.activity_id`；并且
- 通过 `JoinableTeamFactsArguments(activityId: StrictInt, gt=0, extra=forbid)` 的确定性校验。

Prompt 只表述该软性原则；是否真的可以执行仍完全由 Schema、Capability、Registry 与 Orchestrator Harness 决定。

## 4. 认证参数仍然禁止

Prompt 仍明确禁止模型传入 `userId`、`authenticated_user_id`、`token`、`headers`、`auth context`、`SQL`、`base_url`。这些不是 Tool Contract 的模型输入。

硬边界没有变化：`JoinableTeamFactsArguments` 的 `extra=forbid` 仍拒绝携带 `userId` 等额外参数，可信身份仍仅由 `AgentState → AuthContext → JavaMarketClient` 注入。

## 5. Prompt 与 Harness 的职责边界

| 边界 | 职责 |
| --- | --- |
| Prompt | 指导模型从动态 metadata 选择 Tool，使用可信来源的参数，不猜测缺失事实。 |
| Tool arguments schema | 严格校验参数类型、范围和额外字段。 |
| Capability + ToolRegistry | 仅允许已授权、已注册的 Tool。 |
| Orchestrator / Evidence validation | 控制执行、重试、重复调用终止，以及 ANSWER 的证据可用性。 |

没有因为 Prompt 中保留了身份保护文字而放宽任何 Schema 或 Harness 校验。

## 6. 固定 Multi-Tool Workflow

不存在。Prompt 未写入“先查询订单、再查询其它团”的业务规则；它只允许模型使用 user query 或已验证 Observation/Evidence 中的值，下一步 Tool 选择仍属于动态 DecisionModel 行为。

## 7. 修改文件

- `decision/real_llm.py`：将 V1 单 Tool 专属规则替换为 Tool schema 驱动的通用参数规则。
- `tests/test_real_llm.py`：新增 Prompt 文本、双 Tool provider payload 与合法 `activityId` Decision 回归测试。

未修改 Java、Tool Contract、Registry 架构、Observation、Evidence Contract、认证、Provider、`.env` 或 Router。

## 8. 测试

新增测试验证：

- SYSTEM_PROMPT 不再全局禁止 `activityId` 或把 `outTradeNo` 写成唯一参数；
- Prompt 明确引用 `parameters_schema`，并保留身份/凭证/内部系统参数禁止规则；
- captured provider payload 同时包含两个 Tool 的 metadata，分别要求 `outTradeNo` 与 `activityId`；
- OpenAI-compatible DecisionStage 能接受合法的 `get_joinable_team_facts({"activityId": 100123})` Decision；
- V2-5C 原有测试仍验证 `activityId + userId` 被 Arguments Contract 拒绝；
- Evidence、Capability、Auth、RepeatPolicy 与 Dynamic Router 既有测试仍通过。

## 9. Remaining Issues

- 本阶段未进行 V2-5D Multi-Tool 真实 LLM/Java 联调，也未实施任何固定 Tool 编排。
- Prompt 是软性约束；真实 Provider 的 Tool 选择质量和多步事实组合仍需在 V2-5D 以真实行为验收，不能由 Prompt 文本测试替代。
- 当某个 Tool 的必需参数不在用户输入或 Observation/Evidence 中时，目前只能由模型根据现有能力选择下一步或 HANDOFF；未新增询问槽位/Planner。
