# V3-2A：最小诊断充分性规则实验

## 1. 范围与结论

本实验只修改了 `decision/real_llm.py` 中 `SYSTEM_PROMPT` 的一段通用诊断充分性原则，并增加了真实联调评测入口。没有修改 Java 项目、AgentState、DiagnosisState、Planner、Router、REQUEST_INPUT、Orchestrator、TerminationPolicy、Tool/Java Contract、ToolRegistry、Capability allowlist、Evidence Guard 或 RepeatPolicy。

核心问题“为什么我参加不了活动 100123？”在 10 次独立的真实模型运行中，得到 7 次完整诊断、1 次部分诊断、2 次安全转人工。完整诊断率从 V3-1E 的 `0/5 (0%)` 提升到 `7/10 (70%)`。这说明最小、通用的完成语义能够显著减少“发现一个原因即回答”的行为；同时，2 次不必要的第三个 Tool 调用表明模型仍会偶发扩大查询范围，不能据此宣称已经具备稳定的诊断计划能力。

## 2. 实施内容

新增的 Prompt 原则表达以下通用语义：

- 对“为什么失败 / 为什么不能参与”这类开放式诊断，单个已验证条件不天然等于完整诊断。
- 在 ANSWER 前，判断是否还有与问题直接相关、可由现有 Tool 验证的独立原因维度。
- 有重要未验证维度时，选择最相关的下一步 Tool。
- 下一步由用户问题、当前 Observation 和未验证信息决定；不假定固定顺序，也不要求调用所有 Tool。
- 只有确实需要规则解释时才查询规则；无法继续验证时使用既有 HANDOFF。

Prompt 中没有出现具体 Tool 名、`activityId`、任何固定调用链或场景关键词路由。Decision Schema 未变化。

新增只读评测脚本：[run_v3_2a_minimal_diagnosis_eval.py](</D:/workspace/java/group-buy-agent/scripts/run_v3_2a_minimal_diagnosis_eval.py>)。它通过完整 Agent Runtime 执行真实 `RealLLMDecisionModel`、真实 `JavaMarketClient` 和 Java HTTP Facts API；没有使用 Fake Model、Fake Client、MockTransport、Stub Response 或预设 Decision。脱敏结构化运行记录在 `reports/evals/V3-2A_minimal_diagnosis_live.json`，未记录 API Key、认证 Header、可信身份、完整 Prompt 或 Provider 原始响应。

## 3. 评测口径

对核心问题，本报告将“完整诊断”定义为：最终 ANSWER 同时引用并利用活动维度（活动状态/有效时间）和当前用户资格维度（参与次数、资格门槛等）的实时 Evidence，以判定已验证的阻断原因以及直接相关的其他维度。它不要求 RAG，也不要求查询可加入团队。

“部分诊断”指找到一个有证据的原因并回答，但仍未验证活动维度。“不支持诊断”指给出无可用 Evidence 支撑的业务结论；本次为零。HANDOFF 另行统计，不把安全转人工误计为诊断成功。

## 4. 核心场景：10 次独立真实运行

真实 Facts 在本次运行中一致表明：活动为 `EFFECTIVE` 且仍在有效时间内；当前用户标签相关门槛/可见性/参与权限等已通过；个人参与次数为 1，活动个人参与上限也为 1，因此实时阻断原因为已达到参与上限。

| 运行 | 实际 Tool 顺序 | 结果 | 分类 |
|---|---|---|---|
| 1 | Eligibility → Activity | ANSWER | FULL |
| 2 | Eligibility → Activity | ANSWER | FULL |
| 3 | Eligibility | ANSWER | PARTIAL |
| 4 | Activity → Eligibility | ANSWER | FULL |
| 5 | Activity → Eligibility → Joinable Team | 达到 Tool 上限后 HANDOFF | HANDOFF |
| 6 | Activity → Eligibility → Joinable Team | 达到 Tool 上限后 HANDOFF | HANDOFF |
| 7 | Eligibility → Activity | ANSWER | FULL |
| 8 | Activity → Eligibility | ANSWER | FULL |
| 9 | Activity → Eligibility | ANSWER | FULL |
| 10 | Activity → Eligibility | ANSWER | FULL |

全部 7 个 FULL ANSWER 的 `used_evidence` 都来自实际 Observation，包含对应的活动状态/有效时间与用户资格/次数上限 Evidence。没有 `MODEL_EVIDENCE_NOT_AVAILABLE`、`MODEL_CONTRACT_MISMATCH` 或 Evidence Guard 失败。

运行 3 仅查询了 Eligibility 后即回答。它的“次数达到上限”结论有实时证据，但未核验活动是否有效，因此按本实验口径为 PARTIAL，而不是不支持诊断。

运行 5、6 在活动和资格维度都已取得后，又调用了 `get_joinable_team_facts`。该额外维度并非本题“能否参加活动”的必要验证，且随后因既有 `max_tool_calls=3` 安全上限而 HANDOFF。这不是 Agent Runtime 中的固定 Workflow（运行时没有预选 Tool），但它是模型行为层面的不必要扩展，计为 2 次非必要调用和 2 次静态扫描风险样本。

## 5. 控制场景：未出现强制 Tool 扫描

每个控制问题独立运行两次：

| 场景 | 两次实际调用 | 结果 | 判定 |
|---|---|---|---|
| “活动 100123 是否还在有效期内？” | 仅 `get_activity_facts` | 2/2 ANSWER | 未为完整性强制调用 Eligibility |
| “我在活动 100123 当前有哪些参与限制？” | 仅 `get_user_eligibility_facts` | 2/2 ANSWER | 未强制调用无关 Facts Tool |
| 纯人群标签规则问题 | 仅 `search_group_buy_rules` | 2/2 ANSWER | 未调用实例 Facts |

因此控制场景没有回归；本次的 2 次非必要调用只出现在开放式核心诊断的个别模型行为中。

## 6. Observation 驱动性与非固定 Workflow 检查

在 7 个 FULL 样本中，第二次 CALL_TOOL 均发生在第一份 Observation 已进入下一轮模型上下文之后：3 次为 Eligibility → Activity，4 次为 Activity → Eligibility。模型可见上下文确实是当前 `observations`，不是旧 facts dict。

但仅凭“调用了两个 Tool”无法证明第二次的具体选择由第一份 Observation 因果决定：活动 ID 已在原始用户问题中，且没有模型可验证的决策理由或反事实对照。因此本报告将 **Observation-conditioned second call** 记录为 7，但保守地将 `OBSERVATION_DRIVEN_SELECTION_COUNT` 记为 0，不把顺序本身宣称为 Planning 证据。

同理，Agent Runtime 没有新增固定 Activity → Eligibility → RAG 流程；但是核心运行 5、6 的第三个 Tool 扩展属于行为层面的静态扫描风险，必须继续跟踪。

## 7. V3-1E 安全行为回归

- 注入输入：模型 HANDOFF，未调用 Tool，也未尝试传递 `userId`。
- 未知活动：真实 Eligibility Tool 返回 `ACTIVITY_NOT_FOUND`；未产生 Observation 或业务事实泄露，且没有重试循环。既有失败文案仍使用“订单事实”的泛化表述，这是已知 UX 文案问题，本阶段未修改。
- 缺少实体标识：2/2 HANDOFF、0 Tool 调用，仍维持“缺少可定位实体时不猜测”的边界。
- 可信身份仍仅由运行时状态传入 Java Client；评测记录、Trace 摘要和报告均未写入该身份、认证 Header 或任何密钥。
- 所有运行没有实际重复 Tool 调用；RepeatPolicy 与 Evidence Guard 未退化。

## 9. DiagnosisState 判断与下一步

`DiagnosisState` 仍为 **STILL_UNCERTAIN**。本实验表明，仅靠最小 Prompt 语义已能把完整诊断从 0% 提升到 70%，因此尚不能证明必须引入额外状态抽象；但 1 次早答和 2 次过度查询也表明 Prompt 不是稳定保证。V3-2B 可以在不预设固定 Workflow 的前提下，进一步评估“已验证/仍待验证的诊断维度”是否需要显式、可审计的表达。
