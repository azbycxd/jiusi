# V2-9A.2：缺失实时证据最终动作契约修正

## 1. Root Cause

此前 SYSTEM_PROMPT 要求在不可安全回答时 HANDOFF，也限制了 Evidence 必须来自 Observation；但没有明确区分两件事：

- 一般规则/概念已经被规则知识充分回答；
- 某个具体用户、订单、团队、活动、退款或支付实例的当前事实仍然缺失。

因此真实模型偶尔把“我无法确认具体到账时间”的限制性文本视为完成 ANSWER。该文本没有安全幻觉，但不符合当前产品对缺失实例实时事实的 FinalAction 策略。

## 2. 为什么安全 ANSWER 仍不符合当前产品 FinalAction

安全限制性 ANSWER 不会捏造退款到账时间、退款状态或资金状态，因此不是 Safety Failure；但用户的原始请求是实例级退款到账事实。当前能力没有支付渠道退款状态、完成时间或到账时间事实，无法完成该请求。产品契约要求：可先检索一般规则，但最终必须 HANDOFF，并在 `missing_information` 中说明所缺事实或能力。

## 3. General Rule 与 Instance Fact

| 请求类型 | 证据条件 | 合法最终动作 |
| --- | --- | --- |
| “CLOSE 状态是什么意思？” | 规则 Evidence | ANSWER |
| “我的订单现在是不是 CLOSE？” | 对应订单 Facts Observation | ANSWER |
| “退款什么时候到账？” | 当前无退款到账 Facts；规则仅解释边界 | HANDOFF |
| “我现在是否一定有资格参加？” | 当前无用户资格 Facts | HANDOFF |
| “参加活动一般受哪些资格条件影响？” | 规则 Evidence | ANSWER |

## 4. Prompt / Contract 最小修改

仅在 `decision/real_llm.py` 的 SYSTEM_PROMPT 增加通用语义：按完成请求所需的信息而不是关键词分类；一般规则可由规则 Evidence 回答；任何具体实例的状态、结果、资格、时间、金额等只有在可信 Tool Observation 验证后才可 ANSWER。一般规则不能填补缺失的实例事实；即使回复可以说“无法确认”，仍必须 HANDOFF。

没有引入退款、资格、订单等关键词 Router 或固定 Workflow。

## 5. Evidence Guard 与 RAG

- Hard Evidence Guard：未修改。它仍只验证 ANSWER 的 `used_evidence` 是否来自 Observation，不创建 synthetic Evidence，也不把 available tools 当作 Evidence。
- RAG：Catalog、Retriever、ranking、threshold、Tool description 和 `search_group_buy_rules` Contract 均未修改。
- 允许 `RAG -> HANDOFF`：RAG 是一般规则来源，不是用户实例实时事实来源。

## 6. 修改文件
