# V2-9C.1：多跳 Answer Evidence 与参数 Grounding 职责拆分

## 1. V2-9C 唯一阻塞

V2-9C 的 38/42 首轮中，四条 Dynamic Chaining 均已正确执行 `Order Facts -> activityId -> Joinable Facts`，且 Parameter Grounding 为 0 失败；失败只因 Eval 将中间 `activity_id` provenance 机械要求为最终 `used_evidence`。这使 Answer Evidence 同时承担了“最终业务陈述”和“执行参数来源”两种职责。

## 2. 语义审计与职责定义

- **Answer Evidence / used_evidence**：最终 ANSWER 实际陈述或实质依赖的业务事实，且必须来自 Observation。
- **Tool Parameter Grounding / Provenance**：后续 Tool 参数来自哪里。例如 `get_joinable_team_facts.activityId` 必须等于此前 `get_order_facts.references.activity_id`。

`agent.state` 的 Observation、`context.tool_call_history` 的参数记录，以及现有 Eval 的 `parameter_grounding` 断言已经可以完整验证后者。因此不需要新增 Production Runtime Provenance Schema。

若最终答案明确说“订单对应活动 ID 是 100123”，则必须引用 Order Evidence；若答案只陈述“本次查询没有候选团队”，Joinable candidate Evidence 足以支撑答案，中间 activityId 仍由 Grounding assertion 验证。

## 3. Prompt 与 Eval 校准

SYSTEM_PROMPT 改为：多步 ANSWER 只引用最终业务陈述/依赖的事实；Tool 参数来源由独立 provenance 验证，纯中间值不必机械进入 `used_evidence`。没有自动追加 Evidence、synthetic Evidence 或 Harness 改写模型 Decision。

四条 dynamic_chaining Case 保留：

- required tools；
- 固定顺序 `get_order_facts -> get_joinable_team_facts`；
- `activityId <- references.activity_id` 的严格 parameter grounding；
- Joinable 结果 Evidence。

移除了对 `get_order_facts.references.activity_id` 必须出现在最终 `used_evidence` 的错误要求。Multi-source Facts + RAG Case 未修改，仍要求最终业务答案引用两个实际来源。

## 4. Hard Evidence Guard
