# 生产化演进

> 【C 生产扩展，当前未实现】本页是演进设计，不代表当前部署能力。

## 多实例 State

进程内 SessionMemory 在重启后丢失、实例间不可见，并发请求可能覆盖同一 Task。生产可用
Redis/KV 保存 `task_id + trusted identity scope + state_version`，使用 CAS/optimistic
lock，必要时增加 per-task lock 与 TTL。冲突应重读再决策，不能 last-write-wins 静默丢状态。

Checkpoint 保存 Agent Loop 恢复点；Long-Term Memory 用于复用历史信息，两者生命周期、
一致性和隐私目的不同。RedisCheckpointStore 仍是 Stub。

## Redis 的可选角色

Redis 可承担 Session/Checkpoint、Rate Limit、Distributed Lock、Cache、Idempotency 和
Task State，但不是所有能力都必须放 Redis。权威订单事实仍属于 Java/MySQL；知识 Catalog
也不应因方便而失去版本治理。

## 写型 Tool

当前五个 Tool 全是 READ_ONLY，所以“前五个 Tool 已修改数据、第六个失败”的副作用问题
当前不存在。未来 Action Agent 应区分 READ_ONLY、IDEMPOTENT_WRITE、NON_IDEMPOTENT_WRITE。

以 refund_order 为例，执行前必须有可信身份、业务授权、precondition、明确用户确认、
idempotency key；执行中需要事务边界和 action journal；执行后要 result verification、
audit log；失败按可逆性使用 compensation/rollback 或 manual reconciliation。

若 Agent 已执行五个写动作后第六步失败，不能仅靠 Loop 重试。需要 Saga/Compensation、
明确事务边界、幂等、Checkpoint、Action Journal 和人工对账。数据库 rollback 只能处理
同一事务内动作，跨服务业务补偿需要单独设计。

## HTTP 与 gRPC

当前 Python→Java Facts 使用普通 HTTP JSON：开发简单、跨语言、可观测、curl/浏览器调试
方便，当前 QPS/Latency 没有证据要求替换。

高 QPS 内部 RPC、严格 IDL、低延迟、streaming、多语言 SDK 生成需求出现时可评估 gRPC。
Protobuf 优点是 schema、二进制体积和 code generation；代价是浏览器/人工调试不直观、
网关与运维基础设施更复杂。当前项目没有使用 gRPC。

## MQ

当前在线诊断链不依赖 MQ。生产可用于异步长任务、Audit Event、Eval 数据异步落库、
Tool execution event 和 Notification。可靠链路需 producer confirm、consumer ack、有限
retry、DLQ、幂等 consumer 与可追踪 message/task ID；MQ 不应放在同步必需事实路径上增加延迟。

## 上线策略

1. Offline Eval：固定 Contract、安全、Retrieval 与 Gold Case。
2. Shadow Traffic：只观测不影响用户，不执行写操作。
3. Canary：小比例可信流量，设自动熔断/回滚阈值。
4. A/B：比较任务成功、unsupported、handoff、P95、cost 和 safety。
5. Bad Case Monitor：自动分类并进入 Regression Dataset。
6. Rollback：模型/Prompt/Tool/Catalog/代码各有可回退版本。

上线门槛不能只看一个 Accuracy；至少同时约束安全回归、Evidence failure、Task success、
Handoff、P95/P99、Token/Cost 和下游错误率。

## 演进顺序

先测量瓶颈，再增加单项机制：共享 Checkpoint→限流/熔断→容量/性能验证→必要的检索升级。
没有业务数据支持时，不为“架构完整”一次引入 Vector DB、MQ、Redis、gRPC 与多 Agent。
