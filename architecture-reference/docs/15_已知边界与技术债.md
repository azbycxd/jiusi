# 已知边界与技术债

## 已验证但非生产证明

确定性 unittest 证明 Reference Contract 可运行，不证明真实 Provider、Java、网络、Redis
或多实例部署稳定。历史真实 Eval 是阶段样本，不是长期 SLA 或所有业务分布的准确率。

## 当前未实现

- Embedding、Vector DB、标准 BM25 服务、Hybrid/RRF 在线链、Cross Encoder、HyDE、GraphRAG。
- 大规模 Gold Dataset、线上 A/B、正式安全红队和持续 LLM Judge 平台。
- Redis Checkpoint、分布式锁、全局 Rate Limit、生产 Circuit Breaker、Semantic Cache。
- Long-Term Memory、MCP、A2A、多 Agent、Planner、写型 Tool 与审批/补偿系统。
- 正式 P50/P95/P99、容量上限、QPS、单位任务成本、生产 SLA/SLO。

## 当前有意保留的简化

Rule Catalog 仅 15 条，Entry 即 Chunk，词法 Top-3 足够可解释；没有规模/语义收益证据时
不引入向量基础设施。Reference Trace/Metrics 存在内存中，不对接 Prometheus/APM。
TokenBudget 使用估算，不是真实 tokenizer。Circuit/RateLimit/Checkpoint 只做确定性模型。

## 上线前必须补齐

容量压测、超时/重试/熔断联动、共享 State CAS、密钥与 Telemetry 审计、Catalog 发布治理、
Provider/Java 故障演练、数据保留策略、告警与 Runbook。若增加写型 Tool，还必须先完成
用户确认、幂等、业务授权、事务/补偿、Action Journal 与人工对账。

## 不应错误宣称

不能说“RAG 100% 准确”“系统已使用 BM25+向量库”“支持分布式 Session”“已达到生产
P99/SLA”“支持自动退款”“有长期记忆”。A/B/C 标签必须随源码和文档一起保留。

## 技术债触发原则

技术债不是功能愿望清单。每项升级都需要可观察失败作为输入：检索召回下降才考虑 Hybrid，
跨实例恢复成为真实需求才做 Redis checkpoint，职责隔离或并行收益明确才考虑 Multi-Agent。
升级必须同时给出兼容方案、回归样本、性能预算与回滚条件。

## 风险优先级

第一优先级是身份越权、无证据回答和失败误判；第二优先级是 Session 串扰、无限循环和契约
漂移；第三优先级才是成本与体验优化。任何性能优化都不得删除 Evidence/Provenance 验证。

## 负责人检查单

- 新能力是否有明确 Skill/Tool allowlist？
- 新字段是否说明 Schema 与来源？
- 新失败是否区分业务、依赖和基础设施？
- 新指标是否写明分母、阶段和不代表什么？
- C 层概念是否仍明确标注未实现？

## v1.1 单点修正的边界

真实项目 A 层仍是最小 DiagnosisProgress；Reference v1.1 以 Possible/Required、
RequirementResolver、Evidence Obligation 和确定性 Evaluator 细化完成语义。它没有修改
真实 Tool/Java Contract，也没有引入 LLM 证据判断、固定 Workflow、MCP、Multi-Agent、
Long-Term Memory 或生产基础设施。是否把 v1.1 迁回真实工程，需要先做兼容评估与真实 Eval。
