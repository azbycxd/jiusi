# 总体架构

## 定位

本目录是拼团业务诊断 Agent 的可读 Reference。它展示动态 Agent 如何在不把权限
交给模型的前提下，选择任务、获取可信事实、形成证据并安全结束。

## 在线主链

```text
User Request
  ↓
RequestGateway（建立可信身份边界）
  ↓
Router（识别任务） → SkillRegistry → SkillSpec
  ↓
AgentState（完整工作状态）
  ↓
ContextBuilder → DecisionContext（模型可见投影）
  ↓
DecisionModel → Decision
  ↓
HarnessRuntime（确定性约束）
  ↓
ToolRegistry → AgentTool → ToolResult
  ↓
Observation → Evidence → SkillProgress
  ↓
下一轮 Decision / ANSWER / REQUEST_INPUT / HANDOFF
```

## 核心分工

- Router 决定“这是什么任务”，不规划任务内 Tool 顺序。
- SkillSpec 声明能力范围、所需实体、允许工具、诊断维度与完成条件。
- DecisionModel 处理不确定性，提出 CALL_TOOL/ANSWER/REQUEST_INPUT/HANDOFF。
- HarnessRuntime 组合格式、能力、身份、来源、重复、预算、完成度和证据 Guard。
- Orchestrator 推进生命周期，不包含 Activity → Eligibility 等固定业务 Workflow。
- AgentState 保存可恢复运行状态；DecisionContext 只投影本轮必要信息。
- ToolResult 表示执行结果；成功结果才可形成 Observation；Evidence 是精确事实引用。

## 四种结束与暂停动作

ANSWER 必须同时通过 CompletionGuard 和 EvidenceGuard。REQUEST_INPUT 表示能力存在、
但缺用户可补的业务实体，State 进入 WAITING_INPUT。HANDOFF 表示能力不足或不能可靠
继续。Tool timeout 不等价于业务失败，只能按有限 RetryPolicy 处理。

## 动态而非固定 Workflow

参与诊断需要活动状态与用户资格两维，但模型可以先查任意一维。Progress 只记录
v1.1 将 possible 与 query-scoped required 分开，Progress 由 Evidence Obligation 的
PENDING/SATISFIED 派生 remaining；它阻止提前 ANSWER，也阻止完成后探索无关 Tool。
控制问题可以由 Skill 的进度策略缩小为单一维度，避免静态 Tool sweep。

## A/B/C 分层

- A：映射当前真实项目已经验证的边界，如 Tool/Evidence/Harness/身份隔离。
- B：本 Reference 的 Skill、Router、Context 和教学型 Orchestrator 抽象。
- C：文档中明确标注的生产化演进，不冒充当前已部署能力。

本 Batch 不扩展 RAG 检索算法、Eval/Trace 平台或生产基础设施。
