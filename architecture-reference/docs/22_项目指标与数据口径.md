## 三个最容易误读的数字

### 17/20 FULL 不是整体准确率

它只针对同一个开放式参与失败问题、20 个独立真实 Session 的诊断完整性。另 3 次是 Provider timeout 后 HANDOFF；既不能算业务错误，也不能把安全 HANDOFF 当正确业务答案。

### Top-3 100% 不是 RAG 回答 100% 正确

它表示目标规则在当前小型 Catalog 的前三候选中。生成阶段仍可能错误使用证据；规则扩容、别名和长查询也可能改变召回表现。

### 23/23 不是生产 uptime

它是一次最终 HTTP 审计中的固定代表场景。生产 uptime 需要长期监控、流量覆盖、P95/P99、错误预算和依赖 SLA，本项目没有这些数据。

## 失败分类口径

- MODEL_FAILURE：Provider 合约或模型决策问题。
- TOOL_FAILURE：Tool 执行或下游 Contract 失败。
- CONTEXT/RAG/EVIDENCE/HARNESS/BUSINESS：对应产品层设计缺陷。
- INFRA_FAILURE：网络、Provider timeout、Java/Docker 环境不可用；不可偷算为产品 PASS 或 FAIL。

## 报告原则

1. 分母必须写明。
2. timeout 必须单列。
3. 自动测试、检索、行为 Eval、HTTP E2E 是不同层指标。
4. 不得用一次验收推导 P95、QPS、SLA 或生产准确率。
5. 若数据来源不可复现，写“既有阶段记录”，不可伪造新测结果。
