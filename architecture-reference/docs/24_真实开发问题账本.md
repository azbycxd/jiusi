# 真实开发问题账本

以下 12 个问题来自真实项目演进。每项都按“现象—根因—修复—验证—架构教训”记录，避免只记结论。

## 1. Prompt 与 activityId Contract 冲突

- 背景：模型需要为 Activity Tool 生成 activityId。
- 现象：Prompt 示例与 Tool Schema 命名不一致，真实 Provider 返回 contract mismatch。
- 初始怀疑：Provider 不兼容 structured output。
- 排查：对照实际发送 Tool description、Decision JSON 与 Harness 错误码。
- 根因：Prompt 的字段示例落后于 Tool Contract。
- 修复：统一以 Tool 自描述 Schema 为唯一字段源，Prompt 不重复发明字段。
- 为什么有效：模型输出与确定性 Validator 使用同一命名。
- 备选：Provider 侧别名兼容；未采用，避免长期双契约。
- 验证：真实调用不再出现该 mismatch，回归 Schema 测试。
- 架构教训：Prompt 是消费者，不是 Contract 权威源。
- 面试价值：展示如何区分模型问题和接口漂移。

## 2. 空集合 Evidence

- 背景：候选队伍查询可能合法返回 `candidate_teams=[]`。
- 现象：旧逻辑用 truthy 判断，把空列表当“无证据”。
- 初始怀疑：Java 未返回 data。
- 排查：逐层比较 JSON 字段存在性、Observation 和 Evidence path。
- 根因：把“字段存在但为空”与“不存在/失败”混为一谈。
- 修复：按路径存在性判断，保留 None、0、False、[]。
- 为什么有效：空集合是“查询成功且没有候选”的业务事实。
- 备选：添加 `has_candidates` 冗余字段；未强制，避免污染 Contract。
- 验证：empty-list evidence 单测和真实多工具验收。
- 架构教训：事实语义不能依赖语言真假值。
- 面试价值：典型契约边界 bug。

## 3. Evidence 与 Provenance 混淆

- 背景：多跳调用既要证明答案，也要证明下一个参数来源。
- 现象：只校验 used_evidence，模型仍可能凭空构造 activityId。
- 初始怀疑：Argument Schema 不够严格。
- 排查：发现格式合法但值没有用户/Observation 来源。
- 根因：Schema 只验证“像不像”，Evidence 只验证“答什么”，都不回答“参数从哪来”。
- 修复：独立 ParameterProvenance + GroundingGuard。
- 为什么有效：每个 Tool 参数都绑定 USER_INPUT 或 OBSERVATION 路径。
- 备选：把全部参数写死在 Router；会退化固定 Workflow。
- 验证：伪造合法 ID 被拦，合法多跳通过。
- 架构教训：数据形状、调用来源、答案依据是三类 Contract。
- 面试价值：说明纵深安全而非只靠 Schema。

## 4. Deterministic 测试与真实 Provider 差异

- 背景：Fake Model 可以稳定覆盖分支。
- 现象：单测全过，真实 Provider 仍有提前 ANSWER、格式波动或 timeout。
- 初始怀疑：单测实现错误。
- 排查：分开 Contract 单测与 20 Session live eval。
- 根因：确定性测试验证代码边界，不覆盖模型随机性和网络。
- 修复：保留两层测试，禁止 Fake 冒充真实 E2E。
- 为什么有效：代码回归和模型行为分别有指标。
- 备选：只调低 temperature；不能消除协议和基础设施失败。
- 验证：报告同时列 pytest、live FULL/PARTIAL、timeout。
- 架构教训：Eval 必须分层。
- 面试价值：能解释为什么 192 passed 不等于 Agent 可用。

## 5. RAG Rule 不等于实时 Facts

- 背景：规则库能解释参与限制。
- 现象：模型想用规则文本回答某用户当前是否符合资格。
- 初始怀疑：规则内容不够完整。
- 排查：追踪答案引用，发现缺少用户实时 Eligibility Observation。
- 根因：稳定规则与实例状态属于不同事实源。
- 修复：Rule Search 只解释规则；实时判断必须调用 Java Facts。
- 为什么有效：每类结论都有正确 source。
- 备选：把用户状态写入 RAG；会过期且破坏授权。
- 验证：EvidenceGuard 与控制场景 Eval。
- 架构教训：RAG 是知识层，不是事务数据库。
- 面试价值：避免“所有信息都向量化”的常见误区。

## 6. REQUEST_INPUT 与 HANDOFF

- 背景：缺 activityId 时 Agent 有能力但信息不足。
- 现象：旧行为直接 HANDOFF，用户无法同会话补参。
- 初始怀疑：Router 无法识别短回复。
- 排查：检查终态语义和 Session 保存点。
- 根因：把“可由用户补齐”与“能力不存在”合并。
- 修复：增加 REQUEST_INPUT/WAITING_INPUT，仅允许 Skill required_entities。
- 为什么有效：原问题和 missing fields 可恢复，needs_human=false。
- 备选：规则强行从文本猜 ID；不可靠。
- 验证：同 Session 恢复、新 Session/跨身份不继承。
- 架构教训：人机交互状态不是普通错误码。
- 面试价值：体现多轮任务连续性。

## 7. DiagnosisProgress 与提前回答

- 背景：开放式“为什么不能参加”有 Activity 和 Eligibility 独立维度。
- 现象：Progress 前真实评测 14/20 FULL，5 次只查 Eligibility 就 ANSWER。
- 初始怀疑：Prompt 强度不足。
- 排查：比较 Tool 序列和 remaining 信息需求。
- 根因：模型上下文没有显式“已查/还缺”完成状态。
- 修复：真实项目先用最小 goal/required/checked/remaining Progress；Reference v1.1 再以 Evidence Obligation 解除 Tool success 与 Dimension complete 的绑定。
- 为什么有效：完成判断由可审计状态约束。
- 备选：固定 Activity→Eligibility；被拒绝，因为不是动态 Agent。
- 验证：A 层后续 20 次 17 FULL、0 PARTIAL，3 次 Provider timeout→HANDOFF；B 层新增 partial Evidence、双顺序与控制 Query 测试。
- 架构教训：Prompt 原则与确定性完成契约要配合。
- 面试价值：数据驱动决定何时引入 Working State。

## 8. 完成后误调 Joinable Team

- 背景：强调诊断完整性后模型可能过度查询。
- 现象：Activity+Eligibility 已充分，仍调用无关候选队伍 Tool。
- 初始怀疑：Tool 描述过宽。
- 排查：查看 required/remaining 与下一 Decision。
- 根因：只鼓励 completeness，没有“足够后停止”的硬边界。
- 修复：remaining 清空后 CompletionGuard 拒绝无理由扩展；Skill allowed_tools/维度裁剪。
- 为什么有效：完整性不再等于扫描所有 Tool。
- 备选：删除 Joinable Tool；会损失独立能力。
- 验证：最终 unnecessary tool count 为 0。
- 架构教训：既防 premature answer，也防 static tool sweep。
- 面试价值：展示质量与成本双目标。

## 9. Java 端口存活但 Facts timeout

- 背景：健康端口可连接，但 Docker/下游依赖异常。
- 现象：20/20 Tool timeout。
- 初始怀疑：Python timeout 或 Java Contract 回归。
- 排查：分别调用 activity/facts 与 eligibility-facts，检查 Java 下游恢复情况。
- 根因：运行环境依赖未恢复，而非 Python/Java Contract。
- 修复：恢复 Docker/Java 后做连续 preflight；环境失败立即停止 Eval。
- 为什么有效：避免用产品改动掩盖基础设施问题。
- 备选：增加 timeout/重试上限；会放大延迟且制造假 PASS。
- 验证：preflight 连续成功后再跑 Eval。
- 架构教训：端口 alive 不等于业务依赖 healthy。
- 面试价值：展示分层诊断能力。

## 10. Provider timeout

- 背景：真实 LLM 中转 Provider 存在偶发网络超时。
- 现象：开放诊断 3/20 未完成。
- 初始怀疑：DiagnosisProgress 死循环。
- 排查：Trace 区分 MODEL_TIMEOUT 与 Tool/Loop 错误。
- 根因：Provider 基础设施失败。
- 修复：按既有有限重试后 HANDOFF，报告为 INFRA_FAILURE。
- 为什么有效：不输出无证据答案，也不无限等待。
- 备选：自动切 Fake Model；严格禁止。
- 验证：timeout run 终态 HANDOFF，Evidence failure 为 0。
- 架构教训：安全失败也是质量指标。
- 面试价值：准确解释 17/20 的分母。

## 11. Eval Contract error

- 背景：评测 Harness 要区分答案坏与评测器坏。
- 现象：字段缺失时被直接计为业务 FAIL。
- 初始怀疑：Agent Decision Schema mismatch。
- 排查：对照运行 Trace 和 Evaluator 输入，定位缺失发生在评测数据层。
- 根因：Eval 自身 Contract 没有独立 failure category。
- 修复：PASS/FAIL/INFRA_FAILURE 加 MODEL/TOOL/CONTEXT/RAG/EVIDENCE/HARNESS/BUSINESS/INFRA 分类。
- 为什么有效：评测基础设施错误不再污染产品指标。
- 备选：异常全部跳过；会隐藏样本质量问题。
- 验证：failure_classifier 单测。
- 架构教训：Evaluator 也需要被测试。
- 面试价值：体现指标治理意识。

## 12. Capability metadata 不是 Evidence

- 背景：Tool description 会告诉模型“能查询什么”。
- 现象：模型把“Tool 可以查状态”当作“状态已经是 EFFECTIVE”。
- 初始怀疑：Prompt 表述不清。
- 排查：used_evidence 引用了 available_tools 描述而非 Observation path。
- 根因：能力元数据与执行后事实边界未显式约束。
- 修复：EvidenceExtractor 只从成功 Observation 创建引用；Context 中分区展示 Tool 与 Evidence。
- 为什么有效：能做什么不再被当成已经发生什么。
- 备选：隐藏 Tool description；模型将无法可靠选 Tool。
- 验证：EvidenceGuard 拒绝 capability 路径。
- 架构教训：元数据不能升级为业务事实。
- 面试价值：这是 Agent Grounding 的核心边界。
