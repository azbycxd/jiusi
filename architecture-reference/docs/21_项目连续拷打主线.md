# 项目连续拷打主线（45–60 分钟）

使用方式：面试官按编号连续追问。每题先给口述答案，再沿“下一问”进入更深层；不要把 B/C 层说成已生产落地。

## 1. 你做的是什么项目？

口述：这是一个 Evidence-Grounded Business Diagnosis Agent。用户用自然语言提问，模型动态选择只读 Tool，从 Java Facts 或规则 RAG 获得事实，答案必须引用可验证 Evidence；能力不足会 REQUEST_INPUT 或 HANDOFF。

下一问：为什么它不是普通客服 Chatbot？→ 2。

## 2. 与 Chatbot 的差别？

口述：核心不是生成流畅文本，而是把事实获取、参数来源、身份、证据和完成条件变成确定性 Contract。模型只负责不确定决策，不能自行宣称事实。

下一问：整体架构怎样？→ 3。

## 3. 一次请求经过什么？

口述：Gateway → Router → Skill → State/Context → LLM Decision → Harness → Tool → ToolResult → Observation/Evidence → Progress → Completion → 下一轮或响应。

下一问：为什么引入 Skill？→ 4。

## 4. Skill 解决什么？

口述：它把一类任务的实体、可用 Tool、Prompt、Context、完成和失败策略聚合为可审计契约，减少模型暴露面；不拥有独立模型，所以不是 Multi-Agent。

下一问：Router 是否编排 Tool？→ 5。

## 5. Router 和 Planner 的边界？

口述：Router 只识别任务并选 Skill；Skill 内下一动作由模型结合 Observation 决定。代码不固定 Activity→Eligibility 顺序，因此仍是动态 Loop。

下一问：状态放在哪里？→ 6。

## 6. AgentState 与 DecisionContext？

口述：State 是可恢复的完整任务状态；Context 是本轮模型所需的最小投影。认证身份、内部计数和无关历史不进入 Context。

下一问：模型如何调 Tool？→ 7。

## 7. Tool Calling 如何受控？

口述：Registry 明确 allowlist；Harness 检查 Skill capability、参数 Schema、身份边界、参数 Provenance、重复和预算后才执行。

下一问：Java 做诊断吗？→ 8。

## 8. Java Facts 的职责？

口述：Java 负责认证后的权威事实查询，不返回 LLM 诊断结论。Python 将稳定 Contract 变成 ToolResult/Observation，LLM 基于事实解释。

下一问：HTTP 200 是否成功？→ 9。

## 9. ToolResult 为什么单独建模？

口述：传输成功不等于业务成功，要依次验证 HTTP、JSON、Envelope、code、data schema。失败有稳定 error_code/retryable，且绝不生成 Observation。

下一问：Evidence 怎么防幻觉？→ 10。

## 10. Evidence Grounding？

口述：Observation 是成功事实快照；Evidence 是可寻址路径。ANSWER 的 used_evidence 必须逐项解析，伪造路径直接被 EvidenceGuard 拦截。

下一问：参数也是 Evidence 吗？→ 11。

## 11. Evidence 与 Parameter Provenance？

口述：Evidence 支持最终答案；Provenance 证明 Tool 参数来自用户实体或旧 Observation。Schema 只管格式，不能证明来源。

下一问：多步诊断如何避免提前结束？→ 12。

## 12. DiagnosisProgress？

口述：真实项目先用最小 DiagnosisProgress 验证完整性；Reference v1.1 进一步将 Possible 与 Query-scoped Required 分开，并由 Evidence Obligation 的 PENDING/SATISFIED 派生 remaining。Tool 成功不等于维度完整；Condition 可由不同可信路径满足，所以它不是固定 Workflow 或长期 Memory。

下一问：RAG 放在哪里？→ 13。

## 13. RAG 与 Facts 如何分工？

口述：RAG 查稳定规则，Java 查实时实例事实。当前小型规则集使用词法检索，Top-1 70%、Top-3 100%；未实现 VectorDB/Hybrid/Rerank。

下一问：为什么不用向量库？→ 14。

## 14. 为什么当前不用 VectorDB？

口述：15 条左右治理规则规模小、字段强、词法 Top-3 已覆盖当前评测。只有规则规模、语义表达和召回错误证明词法成为瓶颈，才升级 Hybrid/Rerank。

下一问：多轮补参怎么做？→ 15。

## 15. REQUEST_INPUT 与 HANDOFF？

口述：能做但缺 activityId/outTradeNo 等用户可补字段时 REQUEST_INPUT 并保存 WAITING_INPUT；能力不存在或无法可靠继续才 HANDOFF。

下一问：如何恢复且不串号？→ 16。

## 16. Session 隔离？

口述：Memory key 同时绑定 session 与 authenticated identity；同身份同会话补参恢复，跨身份和新 Session 不继承。明确切题则暂停旧任务并创建新 State。

下一问：Prompt injection 怎么挡？→ 17。

## 17. 安全边界有几层？

口述：Prompt 提示、Capability allowlist、Argument Schema、IdentityGuard/Provenance、Java 服务端授权构成纵深防御。恶意文本不能改变可信 RequestContext。

下一问：超时怎么处理？→ 18。

## 18. Retry、Repeat 和 Loop？

口述：Retry 是同一动作的瞬时故障有限重试；Repeat 是模型重复提出相同调用；Loop/Budget 控制全局迭代。超时不是业务证据，耗尽后安全 HANDOFF。

下一问：怎么评测？→ 19。

## 19. Eval 如何分类？

口述：结果分 PASS、FAIL、INFRA_FAILURE，原因分 MODEL、TOOL、CONTEXT、RAG、EVIDENCE、HARNESS、BUSINESS、INFRA，防止把 Provider timeout 当业务错误。

下一问：有哪些真实指标？→ 20。

## 20. 指标如何讲？

口述：当时 Python 192 passed、最终 HTTP 23/23、开放诊断 17/20 FULL 且 0 PARTIAL，其余 Provider timeout→HANDOFF；这是不同样本维度，不能合成生产准确率 100%。

下一问：Trace 记录什么？→ 21。

## 21. Observability？

口述：记录状态转换、模型/Tool 次数和耗时、错误码、handoff/evidence failure；不保存 API Key、认证 Header、完整 Prompt 或异常堆栈。

下一问：并发与生产化怎样？→ 22。

## 22. 当前生产边界？

口述：当前 Memory 为进程内，不宣称多实例一致性、P95/QPS/SLA。生产升级需要 Redis checkpoint、版本/幂等、限流、熔断和容量测试。

下一问：为什么不是 Multi-Agent？→ 23。

## 23. 单 Agent 还是 Multi-Agent？

口述：当前四个 Skill 共享同一模型循环，职责和 Tool 数量仍可控。只有明显的角色隔离、并行任务或独立上下文收益超过通信和一致性成本，才引入多 Agent/A2A。

下一问：如果增加写 Tool？→ 24。

## 24. 写操作怎么设计？

口述：目前全是只读。写 Tool 必须增加确认、幂等键、授权、审计、补偿/回滚和更严格预算，不能复用只读 Tool 的风险模型。

下一问：最大技术债是什么？→ 25。

## 25. 下一步最有价值的工作？

口述：先扩大真实业务评测集并建立线上安全指标，再根据失败归因决定升级检索、Checkpoint 或模型路由；不为了架构名词提前引入 VectorDB/MCP/Multi-Agent。

收束：回到 1，用两分钟讲“问题—边界—闭环—指标—未实现”，确保每个结论都能映射到源码或报告。
