# 性能与成本

## Latency 分解

`E2E = Gateway + Router + Context Build + LLM #1 + Tool #1 + LLM #2 + ... + Response`。
Agent 最大延迟通常来自多轮模型调用；减少一个无必要 Tool 往往也能减少后续一个模型轮。

TTFT 是用户看到首 Token 的时间；Total Latency 是请求到最终动作；Tool Latency 和 Model
Latency 分开统计。P50 表示典型体验，P95/P99 暴露长尾。当前有单次 duration telemetry，
尚未形成正式生产 P50/P95/P99，不能虚构。

## Token 与 Cost

TokenUsage 包含 input_tokens、output_tokens、可选 cached_tokens 和 estimated_cost，并按
Task 聚合。成本受 model call count、Context 长度、Output 长度、Model 选择和 Retry 影响。
CostCalculator 依赖运行时 ModelPricing Protocol，不在源码硬编码可能变化的价格。

## 性能预算

ContextBudget 分别预留 System Prompt、Output、Observation、RAG 和 Tool metadata。Evidence、
当前实体、Progress 与 Schema 不能为省 Token 改写；旧重复说明和低优先级 Observation 可裁剪。

## QPS 与容量

容量模型至少考虑到达率、每 Task 平均模型轮、Provider 并发、Java 连接池、平均/长尾耗时、
Retry 放大与 Handoff 比例。需要分别压测无 Tool、单 Tool、多 Tool、Provider 慢响应和 Java
慢响应，不用单一 hello-world QPS 代表 Agent 容量。

## 指标与优化顺序

先用 Trace 找关键路径，再优化：删除无关 Tool sweep、Context 去重、并行无依赖只读动作（在
语义允许时）、Prompt prefix cache、规则查询缓存、合适模型路由。实时订单/资格不能用纯
语义缓存替代。优化必须同时回归 Correctness、Evidence 和 Safety。

## 当前可报告与不可报告

可报告的是每次 Model/Tool 调用的 duration、次数、可用时的 token usage，以及一次任务的
聚合成本估算。不可报告的是未经代表性压测得到的 P95/P99、峰值 QPS、可用性或正式 SLA。

## 压测场景矩阵

- 无 Tool 的直接能力说明，建立模型单轮基线。
- 单 Java Tool 与单 RAG Tool，分离下游延迟。
- 两个独立事实维度的多轮诊断，观察模型轮次放大。
- Provider 慢/超时、Java 慢/超时、连接失败，检查有限终止。
- 同 Session 并发与不同身份并发，检查状态隔离。

## 成本正确性护栏

降低成本不能通过缩减必要 Tool、删掉 Evidence、复用过期实时 Facts 或跳过 Harness 实现。
每项优化都需同时比较完成率、Evidence failure、unnecessary tool、handoff、latency 和 token。
